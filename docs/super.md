# Super mode

Super mode is for running many tasks at once without switching between sessions yourself. You talk to one session, the **super agent**. For each task you give it, it starts a separate novacode session, keeps track of it on a board, checks the work before calling it done, and tells you when something needs you.

## Starting it

```sh
cd ~/Projects
novacode --super
```

The folder you start in is the super agent's **root**. Tasks can only run in that folder or its subfolders, so starting in `~/Projects` gives it every project below it.

Its session name is always **Super · <root folder basename>**, for example `Super · EEC-Learning`. Resuming an older super session replaces its old name with this fixed name. Conversation-based naming is off, and `/name` explains that the fixed name cannot be changed. Normal sessions and tasks keep their usual naming.

The super agent runs in the background. `novacode --super` starts it if it isn't running and opens a window on it. Closing the window doesn't stop it; run `novacode --super` in the same folder again to reattach. Without a terminal (in a script), `novacode --super` prints the super agent's session id instead of opening a window. `novacode stop <session>` ends it; the next `novacode --super` in that folder resumes the same session. `/kill` in the super window ends it after a confirmation card too, but the next `novacode --super` starts a **new** super session (a new session file; the old chat stays in the old one). Either way tasks keep running, and the board, the charters and Needs you are kept. Run right after a stop, `novacode --super` waits (up to 30 seconds, saying so) for the old super agent to finish shutting down, then starts a new one, instead of attaching to the one that is ending. `-m <model>` picks the super agent's model; without it, the super agent uses your default `model` setting. Other session flags (`--bg`, `-c`, `-r`, `--trust`, `-w`, …) can't be combined with `--super`.

There is one super agent per root, held by a lock file (`super.lock` in its folder, see [The board](#the-board)). Two launches at the same time give one super agent and both attach to it. You can't start one inside, or above, the root of a running one.

## The super agent itself

The super agent is a session with a small tool set: `task` (start and steer tasks; `task info` tells it, before any task starts, whether a folder is in git, which branch a task's worktree would start from, and whether the project is trusted), `ask_user`, `memory`, `todo`, `agent` (subagents, such as a scout that looks something up in a project) and `history_search` (a read-only search of its own past conversation with you). `super.tools` adds more. Its prompt is its own, then your global `AGENTS.md`, then its root folder's own `AGENTS.md` (or `CLAUDE.md` when the root has no `AGENTS.md`; parent folders are not read), each under a tag naming the file; `--no-context-files` leaves out the root's file. It loads no skills or MCP servers, since it doesn't work in any one project. It runs package hooks (Claude Code plugin hooks from packages, such as caveman's or ponytail's mode text added each turn) like any session, but its model gets only the newest copy of each hook message: older copies stay in the session file and are left out of what is sent. Scouts and tasks it starts get the regular tool set (a scout gets `bash` too, not only the scout type's read-only tools), and each runs with its own folder's `AGENTS.md`, MCP servers and trust.

### Its context over days

The super agent runs for days, so its context is rebuilt for every message it gets instead of growing with the chat. Each time, its model gets:

- its prompt;
- a **state block** novacode writes fresh: the board (each task's label, state and last report summary), each task's **charter**, and your **open requests**;
- the newest part of the chat that fits in about 6000 tokens (whole messages; a tool call always comes with its result, and the model's thinking from earlier turns is left out);
- the wake or your message.

Older chat is not resent, but nothing is deleted: the super window still shows the whole history, and the super agent can look things up in it with `history_search` (results capped at about 2000 characters). Since the context no longer grows, the super agent doesn't compact on its own; `/compact` still works but isn't needed.

A task's **charter** is kept on its board row and written only by novacode: the request and acceptance criteria word for word as the task started, its scope, and every decision you made about it since: your answers to its relayed cards, and notes the super agent adds with `task note` (such as "stop before deploy"). When a charter's notes pass 3000 characters, the helper model (the observer's model, see `memory.model`) condenses the oldest ones into one summary; with `memory.enabled: false` there is no helper, so the oldest notes are cut and the cut is marked. The review of a task sees its charter's notes too.

Your **open requests** are things you asked for that are not tasks (yet). The super agent keeps them on its `todo` list, and its open items appear in the state block.

The super agent's rule is that no decision lives only in the chat: a decision about a task goes on its charter with `task note`, a lasting preference goes to `memory`, and a request that is not a task yet goes on `todo`. After each of your messages, the helper model checks whether it held a decision the super agent didn't record; if so, the super agent is woken with a one-line reminder to record it. Only lasting decisions count (a task's scope or limits, a preference, a rule) that its state block (charters, open requests), memory or what it just recorded doesn't already cover; one-off requests ("just this once"), instructions it already carried out, and how its own tools work inside are not decisions. With `memory.enabled: false` this check is off.

Two guards keep tasks on what you asked for:

- **Scope changes need your OK.** A task's scope is a list of short points (at most 8, each at most 25 words; a longer one is refused with the limit, and a scope from an older board counts as one point). To change a task's request, criteria or scope, the super agent calls `task scope`, which opens a card made by novacode showing only the change: the new brief with the old one after `(was: …)`, cut to 30 words, and for criteria and scope the `Added:` and `Removed:` points and `Kept: N points`. Only when you pick "Change" does novacode update the charter, note the change, and send the task the new brief and criteria (as new work, so its review starts over). A plain message to a task never changes its criteria, and reviews judge against the charter.
- **Approvals go through cards.** A task is told that when it needs your approval or decision it calls `ask_user` (or reports `blocked` with a question), and never ends a turn waiting for approval in plain text, which nobody reads.
- **Tasks check conflicting orders.** A task is told that when a message from the super agent conflicts with its brief or with your recorded decisions, it asks you (on a card relayed to the super window) and names the conflict, rather than just obeying.

The super agent's job, as its prompt states it, is to finish every task and close it, fast and accurately, while you are away: it orchestrates, organizes, plans and executes. It never leaves a task blocked, or ready but not landed, with only a status report: it investigates (with scouts), picks a fix and sends it, or asks you one decision with its recommendation. It acts alone on investigation, sending fixes, retrying reviews and failed merges, and replacing a stuck task (`replaces`). Merge, deploy, scope changes and deleting anything still need your card.

The super agent is also told not to ask you on a card before read-only investigation (it just starts it), not to ask a task again for facts novacode already checked (a report's checks, commit and changed files, the proof log), never to tell a task to skip its `report`, never to start a task that edits novacode's settings, and to put deploys and live checks in spawn's `after` steps rather than in the acceptance criteria.

### Health checks and progress

While at least one task is `running`, the super agent is woken every `super.watch.everyMinutes` (default 30) for a **health check**. No task running means no timed check (a stalled task still wakes one, see below), and a check never comes while the super agent is working or while an earlier check still waits for it.

For the check, the state block has a **Health** line per running task, written by novacode from the task's events: how long ago its last event came, which tool is running and for how long, how many tool calls in a row failed, how many times in a row it made the same call, how many of its cards wait for your answer and since when, and how long ago its last progress report came.

- **All fine:** the super agent answers only `OK`. That turn is hidden from your window and left out of the super agent's own chat window; the time of the check goes on the board (`board.md` shows "Last health check"). The super window shows no `cache miss` notices: its context is rebuilt for every request by design (misses are still logged in `~/.novacode/logs/cache-misses.jsonl`).
- **Stalled tasks:** a task is **stalled** when it is `blocked`, `stopped`, or `ready` without a landed merge (a local merge or a merged PR; an only opened PR doesn't count), no question to you about it is open (a `say` question naming it, its own relayed card, or novacode's deploy card), and neither it changed nor the super agent acted on it (`task send`, `review`, `merge`, `accept`, `scope`, `note`, `close`, or a `say` question naming it; the time is kept on its board row) for `super.watch.stallMinutes` (default 15; `0` turns this off). A check lists each stalled task under **Stalled** with how long it has been left alone, and then `OK` is not an answer: the super agent must take a concrete action on each. A task that newly stalls wakes a check by itself, even when the timed check isn't due and no task runs (once per stall). If the super agent's reply takes no action on a listed task that didn't change either, novacode nudges it once with a `[stall check]` note naming those tasks.
- **A problem:** the super agent first asks the task (`task send` with `question: true`). Then it may send instructions, stop the task, resume it or start a replacement task without asking you (with `replaces`, so novacode closes the old one). It never merges, closes, changes scope or deletes without your card, it always tells you what it found and did, and when anything is unclear it asks you first.

**Progress reports.** Tasks are told to call `report` with `state: progress` at each milestone: what is done, what is next, and a count or percentage when known. When a task has worked for `super.watch.progressMinutes` (default 20) without one, novacode asks it for one at its next tool boundary; the task is not interrupted, and nothing is sent while it waits on your answer. Progress reports never wake the super agent; they show on the board and in the state block with their age.

### Messages to you

The super agent sends every message to you with its `say` tool, and novacode draws each one as its own framed block, so you can tell what is new and what kind of message it is even after hours away.

- **Kind:** a coloured badge: `UPDATE` (task news), `QUESTION` (it needs your answer), `WARNING` (something is wrong), `DONE` (work finished), `NOTE` (an aside) or `REPLY` (its answer to your message). A high-priority message carries a reversed badge and `HIGH`.
- **Time and trigger:** the local time it was sent, and what started that turn: `reply to you`, `health check`, or the event, like `after T2-api reported blocked`. Novacode works the trigger out itself. Its own nudges (a decision check, the reminder to use `say`) are never the trigger: the message names the event before them. When several wakes arrived together, it names the task event rather than the health check.
- **Task subtitles:** each message contains a separate subsection for each task it discusses, even when there is only one. Under its task label come its own facts: for a question, its board status line and structured context; for other kinds, three plain lines: **Done:** (what finished), **Next:** (what happens next and who does it) and **Needs you:** (the one thing you must do; left out when there is nothing). Unrelated content goes under **General**. No extra divider lines separate these subsections.
- **Task status lines:** written by novacode from the board, not by the model, inside the matching task subsection of a question: label, state, a percentage and the summary of its last report, and how long ago that report came. General has no board status line. Older saved messages keep their board status line, **Where things stand** and body.
- The choices of a question and, once you answered, your answer follow the subsections. Older saved messages without subsections still replay in their original layout.

Novacode checks every message before it is shown. Outside questions, every task subsection needs `done` and `next` (`needs_you` is optional, General needs `done` or a `body`), the whole message is at most 60 words (longer is refused, for example `message: 61 words, at most 60`), and commit SHAs (7 to 40 lowercase hex characters with a digit and a letter), `proc_<n>` process ids and `PID` are refused with a reminder to use plain words; the super agent sets `detail: true` to allow them only when your latest message asked for those details. Task labels must be on the board (or be `General`), each label appears only once, and a question needs choices unless it asks for one exact answer (a name, a number). Each question subsection instead requires structured context: **What you requested**, **Verified result**, separate **Blocker** entries with **Evidence** and **Impact**, **Why your input is needed**, **Recommendation**, **Risk**, **What stays unchanged**, and the precise **Decision**. Missing or blank fields are refused. Each field is a short point: at most 40 words per field and per blocker issue, evidence and impact, and at most 5 blockers; a longer one is refused with the limit (for example `recommendation: 63 words, at most 40`). The transcript and answer card show these headings beneath the task subtitle, each field as a bullet under its heading. The super agent's `ask_user` is short too: each question text at most 40 words and each option description at most 25 words; `ask_user` in other sessions has no such limit. Explicit unknowns are valid; General questions can truthfully explain why technical blockers are not applicable, without inventing a task or an error. Only a question may have choices: a question is always its own message, so a `done` or an `update` that ends by asking something is refused, and the super agent sends the question next. A question with choices also opens an answer card; the card's label names the tasks and its text keeps the same task subtitles, status lines and facts. When several things happened, you get one block per event, not one summary.

For every kind of message, the super agent assumes you have not read the task sessions and gives the complete picture briefly, in plain everyday words, with no commit SHAs, process ids or test counts unless you asked: it explains jargon, separates verified facts from unknowns, and gives a concrete next action. Before asking you about a task blocker, it asks the worker for the exact failed command and error, the behaviour still needing proof, the impact, and the proposed next step. Missing evidence stays explicitly unknown, never invented. Question choices identify whether they answer a question, **prepare a plan only**, or **execute changes**; code labels the latter two explicitly. Approval to prepare a plan is not permission to execute it. This structure checks that explanations are present, not that model-supplied evidence is true. Older saved questions keep their original content layout. Long answer cards keep the selected choice/input and help visible; use **Page Up/Page Down** to read the question context and preview, and arrow keys to move through choices. A choice that has not been shown cannot be confirmed by an unseen number shortcut.

The super agent's plain text is never shown as it is. If it ends a turn with plain text instead of a message, novacode holds the text back and asks it once to resend it through `say`; plain text again is shown as a `NOTE` block, and only that block. Plain text after a message in the same turn is a recap of what you already got: it stays hidden and out of the super agent's later context, with no reminder. Both stay in the session file. The `OK` of a health check that found everything fine stays hidden.

The confirmation cards novacode makes itself (merge, close, scope change, accept, resume after a restart) also start with the task's status line.

**New since you last looked.** In an attach window (the super window is one), a `━━ new since you last looked ━━` line sits before the first message that arrived while the terminal was unfocused. When you attach again later, it sits before the first message newer than the last time one of your windows on that session lost focus or closed (kept in `~/.novacode/seen/<session>`). This needs a terminal that reports focus (in tmux: `set -g focus-events on`); without focus reports, only reattaching places it. A terminal reports focus only when it changes, so a window counts as unfocused from the moment it opens until it gains focus or you press a key, click or paste.

**Needs you.** Open questions and warnings are listed at the top of the Tasks tab under **Needs you**, and are kept on the board, so they survive a restart. A question leaves the list when you answer its card (a question you answer by typing leaves with the super agent's next `REPLY`); a warning leaves when the super agent sends an `UPDATE` or `DONE` about one of the same tasks. Press `d` on a row (with the panel focused) to dismiss it yourself. The super agent sees the list in its state block. A question whose card was open when the super agent stopped opens its card again after the restart (once a window is open); your answer takes it off the list and is passed to the super agent.

## How it works

- You describe a task. The super agent writes 1–5 **acceptance criteria**: checkable statements of what "done" means. For a non-trivial task it shows them to you first, with the branch the task's worktree would start from; if you ask to see them first, it asks you on a form and waits for your answer before it starts the task.
- Steps that can only happen after the merge, such as a deploy or a check of the live site, are not criteria: they are the task's **after steps** (`after` on spawn). They show on its charter and in `board.md`; the task is told they run only after the merge lands and not to do them before; its review lists them as "runs after merge, not judged now" and judges only the criteria. See [After steps](#after-steps).
- It starts a **task**: a separate background novacode session, labelled like `T7-fix-parser` (`T<n>-` plus a short slug of 1–4 words). Each super session numbers its tasks from `T1`, review tasks included; after `/kill` the next super session starts again at `T1` (`novacode stop` resumes the same session, so its numbers go on). A task's id and its worktree and branch names carry the last 4 characters of the super session id that started it, like `.worktrees/bb12-T1-fix-parser` on branch `worktree-bb12-T1-fix-parser`. The super agent, `board.md`, the Tasks tab and `/watch` show the current session's tasks as `T1-fix-parser` and another session's as `aa34·T16-fix-parser`; tasks from before this change keep their names and show as `old·T16-fix-parser`. The super agent can name a task by `T1`, `T1-fix-parser`, `aa34·T16`, `aa34-T16` or its full id; a bare `T16` that only another session has still works, and one that several older sessions have is refused with the candidates. For open-ended work it can give the task a goal made from the criteria you approved; the goal starts without another approval card.
- A task that changes code gets its own git worktree (`.worktrees/<id>`, branch `worktree-<id>`), started from the branch your main checkout has checked out, and its edit tools can't change files outside it (shell commands aren't fenced; this guards against mistakes, not against a task set on doing it). A task that only reads or answers a question runs in place. A read task that turns out to need changes moves itself into a worktree with `enter_worktree`; from then on it is treated as a write task, with its worktree, branch and base recorded, so it is reviewed, merged and closed like one. In a folder without git, a task that changes files runs in place, one at a time per folder (until the earlier one is closed), and is still checked and reviewed; it can't be merged, so once it is ready the super agent offers to close it. A task that changes code can't run in a git submodule (it would edit your submodule checkout in place); a read task runs there in place.
- Tasks are regular sessions in their project: they load the project's `AGENTS.md`, skills and MCP servers (for example codegraph) and follow your normal permissions. If a project isn't trusted yet, the super agent asks you once before its first task there.
- Untracked project files listed in `worktree.copy` (by default `AGENTS.md`, `CLAUDE.md`, `.mcp.json`, `.codegraph/`, `.claude/`, `.novacode/`) are copied into each new worktree, so a gitignored `AGENTS.md` isn't lost. Codegraph's `daemon.*` lock files and sockets are never copied, so codegraph starts its own daemon for the worktree, and a folder holding its own git repo is never copied. Only `.codegraph/` is tool state: nothing in it counts as the task's changes, and it is deleted with the worktree. In any other copied folder (such as `.novacode/` or `.claude/`), the copies left unchanged don't count, but a file the task adds or edits there is work and keeps the worktree. A copied file counts as the task's change once the task edits or commits it, and is then kept; an unchanged copy never counts.
- The super agent doesn't read code or task transcripts. It only gets each task's short reports, which keeps its own context small, even after days.
- Every message about a task names its label; a question also carries its board status line.

## Questions and approvals

When a task asks you something or needs an approval, the form appears in the super agent's window with the task's label in front, like `[T7-fix-parser] Which config file?`. You answer it there. You can also attach to the task and answer there; the super window's copy then closes. (If you answer in the task's window while the super agent is down, the super window's copy may stay open until you dismiss it.) Stopping the super agent never answers a task's card: the card stays open in the task, and you can answer it in the task's own window or in the super window after the super agent starts again.

An unanswered question waits until you answer it. You get a desktop notification (off with `notifications.enabled: false`). Every card waiting for you in the super window (the super agent's questions and `ask_user`, the cards novacode makes, and relayed task questions and approvals) is asked again every `super.watch.remindMinutes` (default 30; `0` turns this off) until you answer or dismiss it: a desktop notification and a short line in the super window, `<task>: still waiting for your answer: <the decision, first 15 words>`. A reminder doesn't wake the super agent's model, so it costs nothing.

The super agent is woken by code, not by polling: a task's terminal report (`done`, `blocked`, `failed`), a review verdict, a merge result, a task's reply to a question (also when that run ended on an error or a limit), or a turn that ended without a report each start a turn of the super agent's with a one-line note. For a turn that ended without a report, the note carries the task's last message (cut to 600 characters), so an answer the task gave in plain text isn't lost. Smaller news (an answered card, a reconnect) rides along with the next wake.

## Done means proven and reviewed

A task can't call its work done on its own word:

- **Proof is checked by code.** novacode logs every command a task runs and marks each result `[proof #N]`. A task that changes code cites those numbers as its checks, so their real exit codes go into the report. A check that is still running in the background doesn't count. A check that ran before the last change may be cited (for example the failing run before a fix) and is marked "(before the last edit)" in the report, but a finished change needs at least one check that ran after its last edit. Besides proof numbers, checks may only name files a check produced (screenshots, logs), which must exist and be newer than the last edit, and URLs; never source files, commands or results, which go in the report's summary. The log is saved in the task's session, so after `/reload` or a resume its numbers still count and new ones continue from them. Files a command changes count as edits too: in a git repo from git's list of changed files, elsewhere from a scan of the folder (skipping `.git`, `node_modules`, `target`, `__pycache__` and dot-folders, and `*.pyc` files); a folder of more than 20000 files isn't scanned, and each proof mark there says "bash edits not tracked in this folder (over 20000 files)".
- **Committed work only.** A task can't report done with uncommitted changes. Untracked files under a `worktree.copy` folder (such as `.novacode/` or `.claude/`) don't count here; other untracked files and changes to tracked files do (closing still keeps a worktree that holds such files). If a task switches its worktree to another branch, the board row takes that branch when the task reports it, and the task's charter gets the note "branch changed from <old> to <new>"; the done facts and the review then use that branch's `HEAD`, and the changed files are counted from where it left the base (`merge-base`). The review checks exactly the commit the task reported; if the task changes its branch during the review, that review is thrown away and a new one runs later. If the task reports done on a new commit while a review runs, that review is stopped and a new one starts on the new commit.
- **Every code change is reviewed.** An independent review task, using the super agent's current exact provider/model and actual thinking level, gets the request (with every follow-up the super agent sent the task later, such as "also add a README line"), the criteria and the changes, but not the task's own summary. It shows on the board as its own row, labelled like `T8-review-T7-fix-parser`, and is archived once its verdict is in. It works in its own scratch copy of the task's commit (`review/<id>/work` in the super agent's folder, on disk rather than in `/tmp`, since builds there can be large; with the `worktree.copy` files), so nothing it runs leaves files in the task's worktree; its edit tools can change files only there. Its commands may write its whole scratch folder (`review/<id>/`, where it puts a base checkout next to `work`), also in the credentials-only sandbox, where the rest of `~/.novacode` stays read-only. It:
  - judges each acceptance criterion as met or not, with proof; an approval must name every criterion by number, one short line each (like "Criterion 1: met, #3 passes"), or novacode refuses it; an approval with a criterion called not met is refused too;
  - sees each check the task cited as novacode recorded it: the command, its folder, its exit code, whether it ran before the last edit, and the end of its output (the last 40 lines, at most 4000 characters), never the task's own words about it;
  - sees the questions and approval cards the task put to you through the super agent, with your answers, as novacode recorded them (the last 10, each cut to 200 characters), so an answer you gave (such as which port to use) isn't flagged as the task's own choice. A card answered in the task's own window is recorded without the chosen answer, a card that was gone when the super agent reconnected is recorded as "closed in the task (answer unknown)", and an approval card is recorded without its options; answers are cut to 200 characters too;
  - re-runs the checks and opens screenshots and URLs;
  - runs the tests and builds for the changed code and the code that uses it;
  - reads the changes for new bugs and for anything the request didn't ask for;
  - for a bug fix, confirms a test fails before the fix and passes after it.
- A test that fails twice on the commit the task started from is reported as **pre-existing**, and one that fails there but passes on a re-run as **flaky**; neither is blamed on the task. These results are kept per repo, base commit, folder and command (in `baseline/` in the super agent's folder), and reused, so there's no full test run at every task start.
- The reviewer can ask for more proof (a browser check with a screenshot, a test, a reproduction). Findings and proof requests go back to the task word for word, once: a task gets 2 reviews that count, and if the second one doesn't approve either, you are asked. If you want the work as it is, after that or at any time before, the super agent's `task accept` opens a card made by novacode, "Ship <label> without an approved review?"; on yes the task becomes `ready`, marked `accepted without review`, and a review still running is stopped. Without your yes on that card it stays as it was. This works on a task that changes code in any state but `queued`, `merging`, `ready` or `archived`, and only when its branch has commits past its base; with nothing committed, accept is refused. Review stays the default.
- If the reviewer itself crashes, a new one starts once; if that crashes too, you are asked, with the reason. A reviewer that hits a provider limit hasn't crashed: it waits for the limit like any task and continues when it clears. If the reviewer's model can't be used (denied, unknown, or not logged in), the task is blocked with that reason.
- Only an approved review, or your yes on that card, makes a task that changes code `ready`. An approval belongs to the commit it reviewed: if the task later reports done again on that same commit (for example, after a merge failed on a dirty main checkout and you cleaned it up), it goes straight back to `ready` without a new review. New work the super agent sends after the approval ends it: the next done is reviewed again, even on the same commit. If the super agent doubts an approval, it orders a second review, which takes the task out of `ready` again without using up a round (nor does that review's restart after a crash).
- A **read task** (a question, nothing to change) reports its answer; the super agent judges it and marks it `ready` (`task accept`, which also stops a review of it that is still running), or orders a review task for it too. While no review runs, the task shows `reviewing (your call)`: nothing else will move it, and the super agent is told to judge it right away. A read task is told to report first, with the direct answer in its short summary (at most 80 words, which is what the super agent reads), and then write its full answer as its final message. If a read task answers in plain text without reporting, it shows `blocked`, and the super agent can still accept a good answer (no card needed) or send it on. Once a read task is `ready`, novacode closes it (see [Finished tasks close themselves](#finished-tasks-close-themselves)).

The super agent can tell a task to use named skills.

## The board

The super agent keeps a board of all tasks in its folder, `~/.novacode/super/<root-hash>/`:

- `board.json`: the machine copy, written only by novacode.
- `board.md`: a readable copy.
- `board.json.bak`: the previous copy; a damaged `board.json` is restored from it.
- `inbox/`: reports tasks write for the super agent to apply (bad or unknown ones go to `inbox/rejected/`; a file that can't be read or moved is skipped, not the whole inbox).
- `review/`: the review tasks' scratch folders, removed when each review ends (and at start, for any a crash left behind).
- `baseline/`: the test results of base commits (see above).
- `root`, `session` and `super.lock`: which root this is, the super agent's session id, and its lock.

The **Tasks** tab in the side panel of a super window shows each task's label, repo, state, model, tokens, age and last summary, refreshed every 2 seconds. While a task is running, the panel opens by itself on the Tasks tab, and it becomes the shown tab when the first tasks appear. Press Enter on a row to open that task in a new tmux window (outside tmux, the attach command is printed, with `NOVACODE_HOME=<path>` in front when your `NOVACODE_HOME` is set). The new window gets your `NOVACODE_HOME`, so it finds the task; if tmux fails, a notice shows tmux's error and the attach command.

`/watch` opens every live work task (not review tasks, and not archived, failed or interrupted ones) at once in tiled tmux panes, each attached to its task and titled with its label: up to 6 panes per window, named `watch`, or `watch 1`, `watch 2`, … when there are more. Outside tmux it prints one shell command that opens the same grid in a new tmux session named `novacode-watch`.

| State | Meaning |
|---|---|
| `queued` | Waiting for a free slot |
| `running` | Working |
| `waiting-you` | A question or approval is open |
| `blocked` | Can't go on without you (or waiting for a quota or rate limit to clear) |
| `failed` | Stopped with an error |
| `stopped` | Stopped by you; can continue |
| `interrupted` | Died while super was down |
| `reviewing` | Being reviewed; `reviewing (your call)` for a read task the super agent must judge |
| `ready` | Reviewed (or `accepted without review`); waiting for merge or close (or PR opened; a finished task closes itself) |
| `merging` | Rebasing and merging, or opening a PR |
| `archived` | Closed |

`waiting-you`, `running` and `merging` are the working states. A task that ended up `ready` or `reviewing` keeps that state even if its process exits, since the reviewed commit is what counts.

At most 5 tasks run at once (`super.maxRunning`, at least 1). New tasks over the limit wait, and reviews start before new work; a message to an existing task never waits. Finished tasks that aren't closed yet are not limited: an idle session costs almost nothing. Finished work closes itself (see [Finished tasks close themselves](#finished-tasks-close-themselves)); any other task closes on your OK.

If a task runs out of quota, or a provider's rate limit lasts longer than the normal retries, the task shows `blocked` with the provider and, when known, the reset time. No new task or review starts on that provider until it clears (tasks on other providers keep starting), and you get one notice. When the limit clears, the super agent tells the blocked tasks to continue by itself. A limit counts as cleared at its reset time (15 minutes after it was hit when the provider gave none), and earlier as soon as the provider works again: a task or review on that provider ends a turn without a limit or error, or the super agent's own request goes through on it. A rate limit (not a quota) holds its provider at most one hour, whatever its reset time says; a task that hits it again holds the provider again.

**Quota card.** When the limit is a quota and another provider is logged in and not on hold (the super agent's own provider first, then `claude`, `codex`, `antigravity`), novacode asks at once on one card: "<provider> is out until <reset time, or unknown>. Move <tasks> to <other provider>?" with **Switch** and **Wait**. The card names every task blocked by that quota and every review waiting on it (a review whose turn hit it, or one queued on it). **Switch** moves the tasks as `task model` does (each to its tier on the other provider) and tells them to continue; a review takes the super agent's current model when the super agent runs on that provider, else that provider's `deep` tier, and a live one continues. **Wait** leaves them waiting for the limit, and no more cards come for that quota. Either way the super agent hears the result with its next wake. Only a task's first quota block wakes the super agent: when the limit clears, novacode resends, and the quota is still out, the repeated block doesn't wake it again. Both last until a task on that provider gets past the limit (any other wake about it). A task that hit the limit while merging is not told to continue, since its merge lock is gone: it stays `blocked` and the super agent is told, so it can call merge again.

A task whose turn ends on a model error, or that stops without reporting, shows `blocked` with the reason. A turn that leaves the task's subagents or background commands still running isn't counted as stopped. A goal that pauses (it stalled, used up its runs, or you interrupted it in the task's window) counts as a goal end, with the goal's own pause reason. A task's goal that ends in the middle of a run is judged when the run ends, so a report the task sends later in that run still counts. Such a `blocked` made by novacode is not final: if the task then sends its own report (for example `done`), that report applies as if the task were still running. That is not so for a turn that ended while merging: that task stays `blocked` until the super agent calls merge again, sends it on, or closes it. If a task that changes code keeps stopping without reporting, or reported `blocked` itself (not on a merge), but has committed work, the super agent can order a review of its commits: novacode takes the commit and the changed files from the task's branch, the reviewer is told there is no report and no proof and runs the checks itself, and the review uses up a round. If its branch head is a commit that was already approved, the task goes straight to `ready` with no new review. With nothing committed, that review is refused.

## Controlling tasks

Ask the super agent in plain words, for example "stop T3", "tell T5 to also update the docs", "close T2". It can:

- **stop** a task: the run ends and its queued messages are dropped, but the session stays; a later message continues it, including a goal it was working toward (pressing Esc in an attached task window still keeps queued messages, as today). Stopping a queued task takes it out of the queue; stopping a task under review stops the review. A `blocked` task isn't running, so stopping it is refused with a hint to close it or send it more work. A task that doesn't answer the stop within 15 seconds (a frozen process) has its process ended (SIGTERM, then SIGKILL after 5 seconds; a suspended process is resumed first so it can end), and the super agent is told;
- **read** a task's final message, also while the task is still running;
- **send** a follow-up to any task (the review of that task sees it as part of your request);
- **note** a decision of yours on a task's charter (`task note`), and change a task's request, criteria or scope only after your OK on a card (`task scope`), see [Its context over days](#its-context-over-days);
- **ask** a task for information, such as the raw output of a check or proof that a merge landed: the task answers in text and changes nothing, its state and any running review stay as they are, and its reply goes to the super agent. A plain follow-up, by contrast, sets the task working again and stops its review. A question and a follow-up or merge message never go into the same run: while the task is still on one, novacode holds the other and sends it when that run ends. Held messages are saved on the board, so they survive a restart of the super agent; if the task's process is gone by then, they are dropped and the super agent is told how many. If you abort or take back the super agent's message in the task's own window, so no run took it, it is dropped when the task goes idle and the held one is sent; a message that fails to send also lets the held one go;
- **close** it, only after you confirm on a card: the session is kept, the board row is archived, and the worktree is removed only if its branch is merged into its base. Before removing it, novacode stops your processes still running inside the worktree, or detached programs (with no terminal) holding a file open there, such as a codegraph daemon (Linux only); a program on a terminal, such as an editor or `tail -f`, is never stopped, and nothing is stopped when the worktree has uncommitted work, since the worktree is then kept. Untracked files count as uncommitted work: in a repo without a `.gitignore`, Python caches (`__pycache__`) keep a closed task's worktree; if such a daemon writes into a copied folder like `.codegraph/` while the worktree is being removed, novacode deletes that file and tries the removal once more. It does the same for a review's scratch folder;
- **merge** it, only after you confirm on a card: the task rebases its branch onto your main checkout's current base branch (in its own worktree, without touching your checkout), resolves conflicts, re-runs its checks and reports that it rebased; novacode itself (not the task, whose shell may be sandboxed to its worktree) then checks that your main checkout is still on the base branch, has no uncommitted changes to tracked files, and that the branch still sits on top of it, and fast-forwards it to the branch. A task can't report the merge as done itself. Only if you ask for a PR does the task instead push and open one (before that, novacode runs `gh pr list --state open` in your main checkout; when an open PR's head is exactly the task's reported commit, the task is told to use that PR, by number and URL, instead of opening another; a failing `gh` is ignored; a GitHub remote alone is not a reason; the merge is then finished once the PR is open, and the task shows "PR opened"). A conflict, a dirty main checkout, or a base that moved again after the rebase comes back as `blocked` with the reason; once the cause is fixed, the super agent can call merge again (with a new card) without sending the task back to work, as long as the approval still covers the task's commit or you accepted it without review. If your main checkout has a different branch checked out than the one the task started from, the merge is refused and your checkout is left alone. Only one merge per repo runs at a time; a second one is refused, naming the task that holds the repo. If a merge is stopped, dies halfway, or the task's goal ends without a merge result, the repo is freed and, if your main checkout was left with a merge or rebase in progress or with uncommitted changes to tracked files, the task shows `blocked` with the reason. A task in a folder without git, or a read task, can't be merged; once it is ready, the super agent offers to close a task without git, and novacode closes a read task itself. After a successful merge (novacode fast-forwarded your checkout, or the task reported its pull request `merged`; an only opened PR doesn't count), novacode closes the task itself once its after steps are done or when it has none, see [Finished tasks close themselves](#finished-tasks-close-themselves). The super agent acts on instructions you already gave and doesn't ask again, in text or on a form, before a merge or close card: the card is the confirmation. A PR merged on GitHub by squash or rebase leaves the branch looking unmerged, so its worktree is kept when the task closes.

### After steps

When a task with after steps is merged, novacode sends it the steps as new work, and it shows `running (merged, after steps)`. A local merge counts as merged once novacode fast-forwards the main checkout. For a pull request, the task is told to merge the pull request per the repo's normal flow (its required checks and approvals) and then report `merge: merged`; a task that reports only `merge: pr-opened` gets no after steps. The merge card names the after steps that will follow.

When the task reports `done` on them with proof (the same checks rules as any `done`), it becomes `ready (merged, after steps done)` with no new review: the review already judged the merged work, and novacode then closes it. `blocked` and `failed` work as usual, and a follow-up from the super agent keeps it merged while the steps run. New work sent after the steps are done starts over: the task is unmerged again and its next `done` is reviewed.

If the task's charter holds the steps back (a note or its scope says "stop before …", "before deploy", "don't deploy", "do not deploy", "no deploy", "not deploy" or "without deploy"), novacode doesn't send them: it asks first on its own card, "Run after steps for <label>: <steps>?". On Cancel the task stays `ready (merged)` and the super agent is told.

A task without after steps, including every row of a board from before this feature, closes itself once its merge lands.

**Deploy at ready.** When a write task in git is `ready`, has no after steps, no merge has landed and no deploy decision is recorded, and the super agent's root project file (the `AGENTS.md`, or `CLAUDE.md`, it loads) mentions "deploy" (any case), novacode opens one card: "<label> is ready. Merge and deploy, or merge only?". Either choice is the merge confirmation, so no merge card follows: **Merge and deploy** sets the task's after steps to "Deploy per the project instructions, then verify the deployed revision and health" and starts the merge; **Merge only** starts the merge without after steps. The choice goes on the charter (`deploy decision: …`) and the card is not asked again; a card closed without an answer is noted too and not repeated. While the card is open the task is not stalled, and `task merge` on it is refused.

### Finished tasks close themselves

Novacode closes a task itself, with no card, once its work is confirmed complete:

- a **read task** that became `ready`, after the super agent was woken with its answer (a read task the super agent must judge closes right after `task accept` makes it ready; one approved by a review closes after the wake about the approval);
- a **write task** whose merge landed (a local fast-forward, or a pull request the task reported `merged`; `pr-opened` alone doesn't count) and whose after steps are done, or that has none.

This is `task close` without the card: the task's process is stopped, its row is archived, its session file is kept, and its worktree is removed only by the close rules above (a branch not merged into its base, as after a squash-merged PR of several commits, or uncommitted files keep it, and the result says why). A branch counts as merged also when every one of its commits is in the base as an equal patch (`git cherry`), as after a merge train. The wake about the event says novacode closes the task now, and the super agent's next wake says how the close went. A task in a folder without git is not closed this way: the super agent offers to close it. Any other task the super agent judges finished goes through `task close` and its card.

When the super agent starts a successor to a task (a retry or a recovery task), it passes `replaces: <task>` to `task spawn`. Once the new task exists, novacode closes the old one without a card the same way (its worktree stays when it has unmerged work), and notes `replaces <label>` on the new task's charter. Replacing a task that is merging is refused.

The merge and close cards are made by novacode itself, not written by the super agent's model, so a task's summary can't talk the super agent into skipping them.

## Work in parallel

Tasks run side by side, so they share the machine. Four rules keep that fast:

- **Changed-only checks.** A write task's brief tells it to use the project's own changed-only or fast check when its instructions name one (such as a `verify-changed` script). It runs the full suite only when its brief or the super agent asks for it (integration), and never runs a full suite in parallel with other tasks.
- **CPU share.** Each time novacode starts or resumes a task process, it sets job limits in its environment: `NOVACODE_CPU_SHARE`, `CARGO_BUILD_JOBS`, `VITEST_MAX_WORKERS`, `VITEST_MAX_THREADS` and `VITEST_MAX_FORKS` to N, and `MAKEFLAGS` to `-jN` (added to your own `MAKEFLAGS` unless it already sets `-j` or `--jobs`). N is the machine's cores divided by the write and review tasks running then, this one included and counted up to `super.maxRunning`, and at least 1. A task already running keeps the N it started with: it is not resized when others start or end.
- **Merge train.** When two or more ready write tasks in one repo, on the same base branch, are to be merged, the super agent calls `task merge` with `tasks: [...]` (in merge order; `pr` works as for one task). One card made by novacode lists them all and confirms the whole train. Novacode then makes a branch `train-<sid4>-<n>` from the base (the next free `n`) and holds the repo's merge lock for the first task, which switches to that branch in its worktree, cherry-picks each task's commits onto it in order, resolves trivial conflicts, runs the full check once and reports `merge: rebased` (or, with `pr`, pushes the branch and opens one pull request). Novacode then fast-forwards the base in your main checkout to the train branch exactly as for a single merge, and marks every task in the train merged: each one's after steps run and finished tasks close themselves as after a single merge. If the train fails (a conflict, a failed full check, or a refused fast-forward), the first task reports which task caused it, novacode tells the super agent the train failed, and each task merges alone with `task merge`, one at a time, with no new card (your yes on the train's card stands, once per task). The tasks other than the first stay `ready` while the train runs; a task sent new work meanwhile is not marked merged, and the super agent is told.
- **No polling, no holding back.** The super agent relies on task events and reports and doesn't poll tasks with scouts, a task waiting on a shared resource does other useful work, and a ready task is never held back only to keep the machine quiet: the CPU share and the merge train handle that.

## Models

The super agent picks a tier for each task: `quick`, `standard` or `deep`, weakest first. The tiers follow **the super agent's current provider**: switch the super agent with `/model` in its window, and new tasks run on the new provider.

Each provider has a preset per tier, named by **model family**, not by a fixed model id. Gemini Argon uses the catalog family `gemini`, restricted to base IDs starting with `gemini-` and ending with `-argon`; other members of that family are not deep models:

| Provider | `quick` | `standard` | `deep` |
|---|---|---|---|
| `claude` | `claude-haiku` | `claude-sonnet` | `claude-opus`, high |
| `codex` | `gpt-luna` | `gpt-sol` | `gpt-astra`, high |
| `antigravity` | `gemini-flash` medium | `gemini-flash` high | Gemini Argon; else `gemini-flash` high |

A family becomes its newest model (by its models.dev release date) that the provider's live model list offers, that is logged in and that `models.deny` doesn't block. The live list is fetched about once an hour; when it can't be fetched, the model catalog is used. Antigravity's ids can carry the thinking level (`gemini-3.8-flash-high`), so `quick` and `standard` pick the `-medium` and `-high` variants (or request that level on a plain id). `deep` uses Gemini Argon when usable in that list; otherwise it uses the newest usable Flash at high. Named Flash medium models classify as quick, Flash high as standard, and Argon as deep; a task explicitly assigned deep keeps that tier even when it uses the Flash fallback.

The super agent's state block has a **Models** section: its provider, the model each tier is now, and the provider's usable models with their prices (USD per million tokens). The super agent may give a task another model from that list, or one you named; novacode refuses a model that doesn't exist, isn't logged in or is denied, and says why.

**Overrides** (`super.tiers`, see [config](config.md)):

- `"super": {"tiers": {"claude": {"deep": "claude/claude-opus-5-5:xhigh"}}}` replaces one tier on one provider.
- The older form `"super": {"tiers": {"quick": {"model": "…"}}}` still works and replaces that tier on every provider; legacy `review` overrides are ignored. `deep` overrides still select deep work tasks, but never reviewers.
- On a provider without presets (an API key provider, for example) and without overrides, every tier uses the super agent's own model, and the Models section says so.

**Reviews** use the super agent's **current exact provider/model and actual thinking level** whenever a new review starts, regardless of the work task's tier or model. They do not select a stronger tier or another provider, and ignore legacy `review` and `deep` overrides for review selection. An explicit retry of a blocked review resolves the current configuration again, rather than reusing the blocked review's model. A queued review that never started and waits only because its provider is on hold picks the super agent's current model again; if that model's provider is not on hold, the review starts on it (a model that can't be used leaves it queued). Work task tier selection is unchanged. Reviews remain independent sessions with separate scratch copies for code changes; their evidence requirements and approval gates are unchanged.

**Switching tasks to another provider.** When a provider's quota runs out, ask the super agent to move tasks elsewhere, for example "move all tasks to codex". It calls `task model` with one task or `all` and a provider (or a model): each task gets the matching tier there. One card made by novacode lists every task with its old and new model; only after you confirm does it switch. A running task changes model at once (its prompt cache starts over); a task blocked by a provider limit is told to continue on its new model; a queued one starts on it. Review tasks, archived tasks and tasks without a live session (a resumed session keeps its own model) are refused, with the reason. The super agent switches models only when you ask.

`models.deny` lists models that are never used by any session, subagent or judge, for example `["claude-fable*"]`.

## If the super agent restarts

Tasks keep running when the super agent stops (`/restart` in the super window restarts it in place).

**After an upgrade.** The super agent remembers its binary as it started (the file's path, size, modified time and inode). When the file at that path changes (a new install) and has held still for a second, it waits until it is idle (no run and no tool going; open cards don't count), then restarts itself on the new binary as the same session, the way `novacode stop` and `novacode --super` would. Its windows reconnect, tasks keep running, and its open questions on Needs you open their cards again (see [Needs you](#messages-to-you)); a card novacode made (merge, close, quota) closes unanswered, and the super agent can ask it again. The super window shows `novacode was upgraded to <version>; super restarted`, and the super agent hears it with its next wake. It restarts once per change of the file, so a failed restart is not retried in a loop. When it starts again, it reconnects to the live tasks, marks those that died while working `interrupted`, and asks you once whether to resume them. If no window is open when it starts again (for example, it was started from a script), that card waits and appears when you open a window, as do other notes from the restart. Review tasks that died are restarted by themselves, and a task the super agent went down while starting is started again. A task that was merging when the super agent went down is told, when resumed, not to merge but to check and report; the super agent then calls merge again. A task that doesn't come up within 60 seconds of being started is killed and shows the start error. A resumed task checks its folder and git first, so it doesn't repeat work; its earlier proof numbers still count. If a turn ended while the super agent was away, it is reported only when novacode can tell the turn was the super agent's; otherwise the super agent just gets a note.
